# Authority and Status

## Purpose

This file explains how authority works inside the public PV-PP repository.

The repository contains canonical, supporting, provisional, application, testing, proof, benchmark, and historical materials. These categories are not equivalent. A document does not become authoritative merely because it is public, appears in a numbered folder, or contains the word “canonical” in an older title.

## Controlling rule

**Current owner files govern.**

Where two documents conflict, the current owner specification or current governance document controls over:

- older drafts;
- historical architecture;
- testing notebooks;
- benchmark-specific descriptions;
- publication summaries;
- implementation examples;
- exploratory extensions;
- obsolete files that retain legacy “canonical” wording.

## Core authority layers

### Core framework

The current core framework defines the persistent state, Productive Value, Productive Power, perceived state, viability, and other framework-level objects.

### Operator ownership

The current operator specifications define operator internals and responsibilities.

The active Layer 2 sequence is:

`PPP → Φ → H → G → ℛ → Graph Layer / seed substrate → Π → Π completeness validation → Constraints → Domain Framing → Adequacy → Σ → ε`

No downstream stage may be used to repair an upstream defect.

### Stack and governance

The current stack/governance files control operator ordering, ownership boundaries, interface relationships, and architecture-level status.

### Execution

Σ selects. ε realizes.

Execution may complete, stage, partially realize, abort, or return upstream according to the execution specifications. ε is not a second selector and may not silently repair a failed upstream decision path.

## Important current distinctions

The present framework treats the following as distinct unless an owner specification explicitly relates them:

- actual persistent state and perceived state;
- PP and PPP;
- PV and PP;
- realized PV and retained realized value;
- actual viability and perceived viability;
- memory, retrieval, expectation, and confidence;
- candidate construction and candidate selection;
- selection and execution;
- attempted action and environmentally realized action;
- framework authority and runtime implementation shorthand.

## Bounded attention

The framework recognizes a minimal **resource-bounded attention principle**: only a bounded subset of potentially available signals, retrieved memory, and other decision-relevant information need become active in a decision cycle.

Attention is not a new Layer 2 operator, does not determine truth, and does not select policy.

## Typed relational memory and cooperation propensity

Cooperation propensity is not a global trust scalar, probability score, independent operator, or selector.

It is counterpart-indexed relational decision state/modification derived from typed relational evidence together with current expectation, confidence, perceived conditions, commitments, and safeguards. Its effects are routed through existing framework interfaces.

## Runtime predicates

Runtime predicate labels such as `V_G`, `Q`, `E`, `T`, `R_condition`, and `C` are implementation mappings to framework-owned or scenario-owned requirements.

They are not a second canonical operator stack.

The governing direction is:

`framework authority → runtime mapping → scenario packet`

## Provisional and deferred material

Some architecture may be structurally mature but still await implementation or regression validation.

In particular:

- Layer 4A structural scaling is specification-complete but final promotion remains deferred pending expanded-state / multi-agent compatibility regression.
- selected proof-program reconciliation remains deferred until proof work resumes;
- selected benchmark normalization remains deferred until benchmark/simulation work resumes;
- publication and white-paper normalization may lag the current framework and should not be used as operator authority.

## Proofs, benchmarks, and simulations

Proof documents establish only the claims actually proved in those documents.

Benchmarks and simulations provide bounded evidence about the tested architecture and conditions. They do not automatically promote every tested assumption into framework canon.

## Research papers and public articles

Research papers, white papers, Substack articles, journal submissions, and other publication surfaces may explain or apply PV-PP, but publication status does not create framework authority.

## Historical material

Historical and legacy documents may be preserved for provenance. Their internal use of terms such as “canonical,” “final,” or “reference model” must be interpreted in the context of their own date and branch.

Do not reintroduce historical operator roles or stack sequences without checking them against the current owner files.

## Compact architecture summary

The current `PV-PP Compact Architecture Skeleton v1.0` is a supporting orientation document only. It summarizes the present architecture but does not replace the underlying owner files.
